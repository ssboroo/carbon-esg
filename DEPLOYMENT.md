# CARBON ESG — deployment guide

## Architecture

- Frontend: Next.js App Router on Render Node web service.
- API: FastAPI on Render Python web service.
- Database: Neon PostgreSQL (AWS Singapore).
- Authentication: Neon Managed Better Auth. The Next.js server proxies auth requests on the same origin so browser sessions do not depend on third-party cookies.
- API authentication: EdDSA JWT verification against the branch-specific Neon JWKS endpoint.

## Render Blueprint

The Blueprint is in `render.yaml`. Open:

https://dashboard.render.com/blueprint/new?repo=https://github.com/ssboroo/carbon-esg

Review the two services and apply after the deployment PRs are merged to `main`.

The frontend is a Node web service (not a static site) because it hosts the same-origin Managed Auth proxy and protected server-rendered workspace. Both services use the free plan for an MVP preview. Free services can sleep after inactivity and are not a production SLA.

## Neon configuration

The Neon project `carbon-esg` is in AWS Singapore, PostgreSQL 17. Managed Better Auth is provisioned on the default branch.

The public Auth base URL and JWKS URL are in the Blueprint. The frontend cookie secret is generated by Render and must remain server-only.

- Runtime DB URL: Neon pooled connection string, stored only in the API environment as `DATABASE_URL`. The Blueprint declares this as `sync: false`; enter it manually when configuring the preview service.
- For a free development preview, use only the isolated Neon development branch and its restricted `carbon_esg_app` role. Do not point the preview at the default/shared production branch.
- The runtime role must have `rolsuper=false` and `rolbypassrls=false`; never use `neondb_owner` as the API runtime role.
- Migration DB URL: Neon direct/unpooled connection string, stored only in a secure migration environment. Do not add it to the public web service or the API runtime environment.
- Never commit either connection string or the cookie secret. If `DATABASE_URL` is absent, DB-backed API endpoints intentionally return 503; health checks should still work.

## Local development

API:
```bash
cd apps/api
python -m venv .venv
# activate the virtual environment
pip install -r requirements-dev.txt
uvicorn app.main:app --reload
```

Web:
```bash
cd apps/web
npm install
# Set NEON_AUTH_BASE_URL, NEON_AUTH_COOKIE_SECRET (32+ chars),
# and NEXT_PUBLIC_API_URL in .env.local
npm run dev
```

Localhost origins are pre-approved by Neon Auth. For production, add the exact HTTPS Render frontend origin to the Neon Auth trusted-domain allowlist after Render creates the service URL.

## Database migration safety

The tenant schema is version-controlled in Alembic. It has not yet been applied to the shared Neon main branch. Test it on an isolated Neon branch first. Before exposing tenant data routes, implement verified identity-to-organization membership checks and run the API with a database role that does not have BYPASSRLS.

## Production limitations

- Free Render services sleep and may cold-start.
- Neon free plan has resource quotas and scales compute down when idle.
- Custom SMTP, backups/recovery drills, monitoring, rate limiting, and security review are required before customer production use.
- No tenant CRUD endpoints are enabled until identity membership and RLS migration are verified.
